# CT-006 Identity Persistence Design

## Goal

Create the initial persistence model for CrowdTrace identity accounts and verification requests.
The model keeps the existing numeric user identifiers, stores password hashes under an explicit
`password_hash` field, and protects private identity and verification data from public projections.

## Scope

The initial Flyway migration will create only the CT-006 tables:

- `users`
- `verification_requests`

The current starter migration and its broader profile-oriented user schema will be replaced rather
than followed by an additional migration. This repository is still at the initial schema stage, so
the replacement is intended to be applied to a clean database.

## Database model

### `users`

- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `email VARCHAR(255) NOT NULL UNIQUE`
- `password_hash VARCHAR(255) NOT NULL`
- `display_name VARCHAR(255) NOT NULL`
- `role VARCHAR(32) NOT NULL`
- `account_status VARCHAR(32) NOT NULL`
- `created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL`
- `updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL`

The migration adds indexes for `email` and `role`. Email and password hash are private fields;
display name is the only public identity field in this persistence slice.

### `verification_requests`

- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `user_id BIGINT NOT NULL REFERENCES users(id)`
- `verification_type VARCHAR(32) NOT NULL`
- `evidence_reference VARCHAR(1024) NOT NULL`
- `status VARCHAR(32) NOT NULL`
- `reviewer_id BIGINT REFERENCES users(id)`
- `review_notes VARCHAR(2000)`
- `created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL`
- `reviewed_at TIMESTAMP WITHOUT TIME ZONE`

The migration adds a queue index on `(status, created_at)` and an index on `user_id`. Evidence,
reviewer, and review notes are private and are not part of public user responses.

## Domain model

The JPA `User` entity uses `Long` for its identifier and maps `password_hash` to a field named
`passwordHash`. The password hash is excluded from JSON serialization. `role` and
`account_status` use explicit enums:

- roles: `REGISTERED_USER`, `MODERATOR`, `SUPER_ADMIN`
- account statuses: `ACTIVE`, `SUSPENDED`, `DEACTIVATED`

The `VerificationRequest` entity maps the request lifecycle with explicit enums:

- verification types: `IDENTITY`, `ORGANIZATION`
- statuses: `PENDING`, `APPROVED`, `REJECTED`, `REVOKED`

Verification status is request workflow state, not an authorization role. A verified user does not
receive moderator or Super Admin permissions as a side effect.

## Repository behavior

`UserRepository` retains paged user access and adds an email lookup used by future authentication.
`VerificationRequestRepository` defines the pending queue query ordered by oldest submission first,
plus user-scoped lookup for future ownership checks.

## Tests

Tests will prove:

1. A clean application context applies the initial migration and exposes both tables.
2. Duplicate email persistence is rejected.
3. Enum values persist and load as explicit strings.
4. Password hash is not serialized in user JSON.
5. Verification evidence is not included in public user responses.
6. Pending verification requests are returned in queue order.

## Out of scope

Authentication, password hashing services, login/session lifecycle, authorization configuration,
verification approval endpoints, profile endpoints, and later case/community persistence remain
separate tasks.
